# AGENTS.md

## Purpose

Canonical operational entry point for agents modifying the `gcomneno/gcomneno`
profile repository.

Read this file before making substantive repository changes.

This repository is a curated public engineering profile. Small wording or
automation changes can alter what is publicly disclosed, how current work is
represented, or which facts are presented as authoritative. Treat profile
content as a public product surface rather than as an exhaustive repository
index.

When sources disagree, use this precedence:

1. verified public GitHub state;
2. explicit current maintainer decision;
3. this operational guide;
4. remembered conversation state.

Investigate contradictions instead of guessing.

## Start here

Before substantive work:

1. inspect repository and branch state;
2. verify current public GitHub facts instead of trusting remembered state;
3. read both `README.md` and `README.it.md` for curated-profile changes;
4. inspect `scripts/update_latest_updates.py` and its tests for Latest Updates
   changes;
5. inspect `scripts/sync_selected_project_releases.py` and its tests for
   Selected Projects release metadata changes;
6. inspect `.github/workflows/update-latest-updates.yml` for automation changes;
7. define the smallest coherent change and its verification.

Primary entry points:

- `README.md` — canonical English public profile.
- `README.it.md` — Italian public counterpart.
- `scripts/update_latest_updates.py` — generated Latest Updates block.
- `scripts/sync_selected_project_releases.py` — generated official-release
  cells for Selected Projects.
- `tests/` — profile-generator regression coverage.
- `.github/workflows/update-latest-updates.yml` — GitHub-native scheduled
  fallback and validation.

## Profile contract

The repository presents a selected engineering narrative. It is not a complete
list of repositories, experiments, private work, employers, clients or personal
activity.

Core properties:

- public-first and privacy-safe;
- technically factual and verifiable;
- bilingual where the profile has English and Italian counterparts;
- intentionally curated rather than automatically exhaustive;
- explicit about the distinction between production engineering, research and
  learning in public;
- conservative about claims of releases, upstream integration and maturity.

Do not add a repository merely because it exists or was recently active.

Do not turn the profile into a chronological dump of all work.

## Public and privacy boundary

Only public information that is appropriate for the public profile may be
surfaced.

Never infer, enumerate or expose:

- private repository names or metadata;
- private project contents;
- private client or family information;
- secrets, credentials, local paths containing sensitive context or private
  operational state;
- remembered work that is not independently appropriate for public disclosure.

A repository becoming visible to an agent does not make it eligible for the
profile.

Automation must discover and render public repositories only. Private,
archived or disabled repositories must not become profile content through a
fallback path.

When privacy eligibility is uncertain, fail closed and leave the profile
unchanged until the maintainer decides.

## Curation and generation boundaries

Sections `01` through `04` are manually curated engineering narrative.

Automation must not choose:

- which projects belong in Selected Projects;
- project ordering;
- project descriptions;
- technical-signal wording;
- research versus learning classification;
- which upstream contributions deserve editorial emphasis.

Generated surfaces are deliberately narrower:

- the `Official release` / `Release ufficiale` cells in the Selected Projects
  table are synchronized from public GitHub Releases;
- the content between `<!-- updates:start -->` and `<!-- updates:end -->` is
  generated by `scripts/update_latest_updates.py`.

Do not manually edit generated content unless repairing the generator in the
same coherent change.

## Official release semantics

`Official release` means the latest public, non-draft, non-prerelease GitHub
Release for that Selected Project.

It does not mean:

- a package manifest version;
- a Git tag without a GitHub Release;
- an internal build number;
- a development milestone;
- the newest commit.

If no qualifying GitHub Release exists, render `—`.

Release synchronization may update only the release cell for already-curated
Selected Projects. It must not add, remove, reorder or rewrite project rows.

A normal GitHub `404` from the latest-release endpoint means that the repository
has no qualifying official release; other API/network failures must fail closed
without partial README writes.

## Latest Updates contract

The exact markers are:

```text
<!-- updates:start -->
<!-- updates:end -->
```

They must remain present in both profile READMEs.

The generator may summarize meaningful activity from recently updated public
repositories, but must exclude the profile repository itself and must not
surface private, archived or disabled repositories.

The English and Italian blocks share the same update set and original commit or
release titles. Only profile UI labels and surrounding text are localized.

The generated block is activity context, not a substitute for manual curation
of Sections `01` through `04`.

## Bilingual profile contract

`README.md` is the canonical English profile and `README.it.md` is its Italian
counterpart.

For curated sections:

- preserve the same projects and ordering;
- preserve the same factual claims;
- localize prose naturally rather than mechanically;
- keep links and release facts semantically equivalent;
- do not allow one language to advertise a materially different maturity or
  capability.

For generated sections, update both files in one operation or neither.

## Open source engineering curation

A pull request belongs under selected merged upstream contributions only after
it is verified as merged upstream.

Do not place open, closed-unmerged or merely proposed work in the merged list.

Summaries should emphasize durable engineering signal rather than PR count:
problem diagnosis, bounded changes, tests, architecture, lifecycle ownership,
performance, security, compatibility or maintainability.

The upstream repository is the authority for merge state.

## Research and learning boundaries

Research entries should describe reproducible experiments, mathematical or
empirical analysis, deterministic tooling or other research-oriented work
without overstating predictive or production claims.

Learning repositories belong under Learning in Public only when their current
state is mature enough to represent useful documented study. Do not promote a
newly initialized or draft-only learning repository merely because it is
public.

Do not present learning repositories as production experience.

## Working method

Before changing profile content:

1. verify the public GitHub facts that motivate the change;
2. decide whether the fact belongs to manual curation or generated metadata;
3. inspect both language versions;
4. inspect the relevant generator/test when generated metadata is involved;
5. make the smallest coherent change;
6. review the resulting diff for accidental disclosure or unrelated churn.

During implementation:

- keep generated and curated authority separate;
- do not opportunistically promote unrelated repositories;
- do not expose private context while explaining public work;
- preserve stable links where possible;
- prefer factual capability descriptions over promotional superlatives;
- distinguish released capability from unreleased work on `main`.

## Testing and automation

Canonical generator test suite:

```bash
python -m unittest discover -s tests -v
```

For changes to `scripts/update_latest_updates.py`, verify Latest Updates parsing,
deduplication, localization, render limits and atomic bilingual writes.

For changes to `scripts/sync_selected_project_releases.py`, verify:

- latest-release rendering;
- no-release `—` behavior;
- API failure handling;
- exact one-row matching for every Selected Project;
- no modification of descriptions or ordering;
- no partial bilingual write.

The GitHub workflow is a scheduled fallback. A separate maintainer-local
scheduler may invoke the profile generator more frequently; repository changes
must not assume that local scheduler state is available in CI.

## Known traps

- A recently pushed repository is not automatically profile-worthy.
- A tag or package version is not automatically an official release.
- `releases/latest` returning `404` can legitimately mean no release.
- Latest Updates being fresh does not imply manually curated sections are fresh.
- An upstream PR appearing in a fork is not evidence that it merged upstream.
- Public visibility of a repository does not by itself determine editorial
  inclusion.
- A generated block can overwrite manual edits inside its markers.
- English-only profile edits create a public contradiction even when every
  individual sentence is true.

## Definition of done

Before claiming profile work complete:

- review the final diff;
- confirm no unrelated files changed;
- confirm no private information or repository metadata leaked;
- confirm English and Italian curated content remain aligned;
- verify all release claims against public GitHub Releases;
- verify merged-upstream claims against the upstream repository;
- run `python -m unittest discover -s tests -v` for generator changes;
- confirm the Latest Updates markers remain intact;
- inspect final repository state and report what was tested.

Never claim a check passed unless its result was actually observed.

## Git and review discipline

Keep commits intentional and reviewable.

Do not rewrite published history, force-push, release, deploy or otherwise
mutate unrelated remote state without explicit maintainer approval.

Automated profile commits should remain narrowly scoped to generated profile
data.

## Maintaining this file

Add only durable repository-wide knowledge: public/privacy boundaries,
curation rules, generation ownership, verification gates and recurring traps.

Do not add private repository names, temporary issue state, chat-specific notes,
personal information, secrets or transient TODOs.
